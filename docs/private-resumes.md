# Private resume processing

## Implemented workflow

Offline text extraction supports PDF and DOCX with explicit parsed/unscored outcomes and parser version `text-v2-pypdf6.21.2-docx1.2.0`. There is no OCR, model inference or automatic score. Encrypted PDFs, empty/image-only documents, invalid signatures, excessive pages/text, unsafe archives and XML document types are rejected with safe machine codes. No private document or library diagnostic is logged.

Limits are 5 MiB compressed input, 20 PDF pages, 100,000 extracted characters, 200 ZIP entries, 20 MiB total uncompressed DOCX content, 4 MiB per entry and a maximum 100:1 compression ratio. Duplicate/path-traversal/encrypted/macro members are rejected. XML is checked with entity expansion, external DTD loading and network access disabled, including UTF-16 documents. Extraction runs in a fresh isolated Python subprocess with a 15-second wall timeout and no inherited cloud credentials. Linux also applies 8 CPU seconds and a 256 MiB address-space limit. These process controls are not a filesystem or network sandbox; deployment must retain the library/input checks. Windows tests exercise timeout and input boundaries; they do not prove Linux resource enforcement.

Private storage uses the existing Antideploy account's free S3-compatible bucket. Firebase remains responsible for authentication and Firestore metadata; FastAPI remains the authorization boundary. Credentials stay outside Git/frontend files and must be installed in the existing Render API environment before enabling integration. There is no paid parsing service.

Object paths are server-derived from a hashed verified owner UID and a generated resume ID. Upload tickets expire after 60 seconds, sign the exact content length/type/hash metadata, and require `If-None-Match: *`. A live nonpersonal check verified incorrect length was refused with 403, overwriting was refused with 412, checksum readback succeeded, anonymous reads were refused with 403, and cleanup succeeded. Never log a signed URL. The server independently checks actual byte count and SHA-256 before processing; metadata alone is insufficient.

## API and durable processing

Resume metadata and durable queued/processing leases live in Firestore. Each source upload is immutable; corrections to confirmed skills have a separate optimistic version. Every owner operation derives UID from the verified session, rechecks active-account state transactionally, and uses identical unavailable responses for missing/foreign IDs. Storage keys, raw extraction and lease tokens stay out of responses. Application snapshots must pin source and confirmed-skill versions when implemented.

`POST /api/v1/resumes` initializes an idempotent upload; `GET` lists ten owned records per page. Per-record routes provide retrieval, replacement upload tickets, finalization, transient-failure retry, explicit skill confirmation and deletion. Writes require the current revision. Upload creation has atomic daily limits of five per owner and 100 globally. The Flutter screen provides bounded PDF/DOCX selection, direct private upload, status refresh, editable suggestions, explicit confirmation and deletion, with session isolation and stale-write recovery.

The existing API process runs one worker with persisted 90-second leases, at most three attempts and restart recovery. It independently checks bytes/hash before extraction and only saves results with the current lease and active owner. Failed parsing remains explicitly unscored; suggestions never confirm themselves. On the free Render service, sleeping stops processing; queued work survives and resumes when the service wakes. This is durable recovery, not an always-on processing latency guarantee. `RESUME_UPLOADS_ENABLED=true` and `RESUME_WORKER_ENABLED=true` require the private S3 environment. Frontend origins remain disabled pending real authenticated acceptance.

Pending uploads expire after 15 minutes, with durable cleanup even if the owner is suspended. Deletion clears extracted text and skills and replaces the source with a zero-byte deletion marker. This prevents an unexpired create-only upload ticket from recreating deleted content. Firestore retains only a minimal deleted-ID tombstone, preventing idempotency replay. Cleanup failures remain visibly pending and retriable. A live nonpersonal storage/Firestore check verified owner isolation, stale revisions, content erasure, old-ticket rejection and fixture cleanup; it is not authenticated HTTP acceptance. Application-retention and recruiter access contracts remain to be implemented before resume content is exposed to recruiters.
